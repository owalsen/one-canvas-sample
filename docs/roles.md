# 업무 프로세스 속 역할 정리

기획자, 디자이너, 개발자(프론트엔드, 백엔드)가 one-canvas 업무 프로세스에서 **무엇을 맡고, 무엇을 하지 않는지** 정리한 문서입니다.
전체 흐름은 [업무 프로세스 도식](one-canvas-process.md)을 함께 보세요.

## 이 문서를 읽는 법

| 표기 | 뜻 |
|---|---|
| (규칙) | [`agile-issue-rule.md`](../agile-issue/agile-issue-rule.md), [`one-canvas-rule.md`](../one-canvas/one-canvas-rule.md), README에 이미 적힌 내용 |
| **(제안)** | 규칙에는 없고 이 레포의 문서화 과정에서 정리한 내용. **팀 합의가 필요합니다** |

> 규칙의 Role 정의에는 기획자, 프론트엔드, 백엔드, 앱, QA가 있고 **디자이너는 없습니다.** 디자이너의 역할은 README의 흐름("one-tool에서 열람·코멘트, AI와 대화하며 검수·수정")에서만 확인됩니다. 아래 디자이너 항목 중 규칙에 없는 부분은 (제안)으로 표시했습니다.

## 1. 한눈에 보기

| 역할 | 한 줄 요약 | 핵심 산출물 |
|---|---|---|
| **기획자** | 무엇을, 왜 만드는지 정하고 정책과 수락 기준을 정의한다 | 통합캔버스 초안, 도메인·에픽·스토리(정책, 수락 기준) |
| **디자이너** | 화면을 어떻게 보여줄지 정하고, 디자인 시스템과의 정합을 책임진다 | 시안(Figma), 캔버스 검수·수정, 미보유 분류 (제안) |
| **프론트엔드** | 캔버스와 디자인 시스템을 근거로 화면을 구현한다 | UI 구현, 클라이언트 상태, API 연동, 디자인 시스템 컴포넌트 |
| **백엔드** | 데이터와 비즈니스 로직을 안전하게 처리하는 서버를 만든다 | DB 모델, API 스펙, 서버 로직·예외 코드 |

## 3. 역할별 상세

### 기획자

**맡는 일**
- 요구사항을 받는 즉시 **에픽과 유저스토리로 분류**한다. 원문 요구사항을 그대로 나열하지 않는다. (규칙)
- 도메인, 에픽, 스토리 설명·정책, 수락 기준(AC)을 쓴다. (규칙)
- 성공·실패 테스트는 QA와 함께 쓴다. (규칙)
- 캔버스가 바뀌면 **캔버스를 먼저 고치고**, 이슈 반영을 요청한다. (규칙: 최신성)
- 이슈를 최초로 생성할 때 캔버스를 **확정**으로 표기한다. (규칙)

**하지 않는 일**
- 근거가 없는 항목을 **지어내서 채우지 않는다.** 막히면 그 항목만 질문하고 나머지는 계속 쓴다. (규칙)
- 화면설명에 **백엔드 계약**(API 엔드포인트, 응답 필드명, DB 테이블)을 정의하지 않는다. 그것은 백엔드의 일이다. (규칙)
- 디자인 시스템 편입을 **권하는 문구**를 캔버스에 쓰지 않는다. 사실만 보고한다. (규칙)

### 디자이너

**맡는 일**
- one-tool에서 캔버스를 열람하고 블록별로 코멘트를 남기며, AI와 대화하며 검수·수정한다. (규칙, README)
- Figma로 시안을 작업하고 캔버스 「참고 자료」에 링크를 건다. (규칙: 참고 자료 섹션, 제안: 흐름)
- 시안이 **디자인 시스템에 있는지 Storybook·카탈로그로 대조**하고, 없는 요소를 4분류(`신규 필요` / `variant 값 추가 필요` / `공용화 필요` / `참조 전용(page-local)`)로 구분한다. (제안)
- 신규 컴포넌트가 필요하면 프론트에게 **스펙**(이름, 용도, variant·상태, 사용 토큰, 사용처)을 전달하고, 구현된 결과를 **승인**한다. (제안)
- 시안(Figma)이 바뀌면 기획자와 함께 **캔버스를 고친다.** 시안 변경은 캔버스 파일에 자동으로 잡히지 않는다. (규칙)

**하지 않는 일**
- Figma에만 있는 컴포넌트를 **있는 것처럼 태깅하지 않는다.** (규칙: 디자인 시스템에 없는 컴포넌트를 있는 것처럼 태깅하기 금지)
- 디자인 시스템 컴포넌트를 코드로 직접 만들거나 릴리스하지 않는다. 그것은 프론트가 이끈다. (제안)

### 프론트엔드

**맡는 일**
- **착수 절차를 건너뛰지 않는다.** 스토리 → 에픽 「참조 자료」의 화면 앵커 → 캔버스 화면(배치·카피·컴포넌트 태깅) → 디자인 시스템 import 순서다. (규칙)
- UI 마크업, 클라이언트 상태(입력 상태, 유효성 검사, 전역 상태), 웹 API 연동(로딩·에러 UI)을 구현한다. (규칙)
- 태스크 끝에 **UI 태그**(`[ui: 화면1 ① 카테고리/컴포넌트]`)와 AC 참조를 단다. (규칙)
- 디자인 시스템의 **유지관리를 이끈다**: 컴포넌트 구현, Storybook 등재, 카탈로그 갱신, 공용 승격, 버전 관리. (제안)
- 신규 컴포넌트가 구현되면 디자이너 승인을 받고, 캔버스의 `미보유` 줄이 정식 태깅으로 바뀌도록 알린다. (제안)

**하지 않는 일**
- **캔버스에 없는 레이아웃·배치를 만들지 않는다.** 태깅이 빠진 요소의 컴포넌트를 임의로 정하지 않는다. (규칙)
- `신규 필요` 항목의 화면 영역은 **구현하지 않고 보류한 채 질문**한다. 대체 UI를 임의로 만들지 않는다. (규칙)
- 나머지 3분류는 컴포넌트가 이미 있으므로 화면 영역을 **정상 구현**한다. (규칙)
- 이슈의 「열린 질문」에 걸린 항목은 확정 전에 구현하지 않는다. (규칙)

### 백엔드

**맡는 일**
- DB 데이터 모델링(테이블, 인덱스, 스키마 변경), API 스펙 정의(Swagger 등), 서버 비즈니스 로직(데이터 검증, 보안 처리, 비즈니스 에러 코드)을 구현한다. (규칙)
- 스토리의 정책·AC·예외·권한을 읽고 **Backend 태스크**를 작성한다. 태스크마다 어느 AC를 위한 것인지 AC 번호를 단다. (규칙)
- 화면이 없는 스토리(B유형)는 에픽의 **「흐름도」**(캔버스 「플로우」 계승)를 처리 순서·분기의 근거로 삼는다. (규칙)
- 도메인 `index.md`의 **불변 규칙**(예: 정산 금액 산출 공식)을 모든 에픽에 일관되게 적용한다. (규칙)

**하지 않는 일**
- UI 배치나 컴포넌트를 정하지 않는다. (프론트·캔버스의 몫)
- 이슈·캔버스에 근거가 없는 동작·정책을 그럴듯하게 채우지 않는다. 확정되지 않은 것은 질문한다. (규칙)

## 4. 인수인계 지점

| 누가 → 누구에게 | 넘기는 것 | 확인할 점 |
|---|---|---|
| 기획자 → 디자이너 | 캔버스 초안(에픽·스토리·플로우) | 범위(In/Out)와 완료 기준이 명확한가 |
| 디자이너 → 기획자 | 시안, 미보유 분류 | 캔버스 화면이 시안과 일치하는가 |
| 디자이너 → 프론트 | 신규 컴포넌트 스펙 (제안) | 사용처, 기존 대안이 안 되는 이유, 상태 목록 |
| 프론트 → 디자이너 | 구현된 컴포넌트 (Storybook) (제안) | 시각·용도가 스펙과 맞는가 |
| 기획자 → 개발자 | 이슈(에픽·스토리·AC) | 화면 앵커, 열린 질문, 미보유 분류가 있는가 |
| 프론트 ↔ 백엔드 | API 스펙 | 응답 필드, 에러 코드, 로딩·에러 UI 처리 |

## 5. 모두에게 적용되는 공통 규칙 (규칙)

1. **근거가 없으면 지어내지 않고 질문한다.** 캔버스는 이슈의 단일 출처라, 한 줄을 지어내면 에픽·스토리·테스트로 번진다.
2. **캔버스가 먼저 바뀐다.** 이슈나 코드를 먼저 고치면 캔버스가 낡아지고 "최신성"이 깨진다.
3. **문서 하나만 읽고 착수하지 않는다.** 같은 화면에 대한 정보가 문서마다 나뉘어 있고, 각 문서가 소유한 것이 다르다.

## 6. 참고: 이 문서에서 다루지 않은 역할

규칙에는 **앱 개발자**(네이티브 UI, 푸시·로컬 저장소 등 디바이스 기능)와 **QA**(테스트 케이스, 회귀 테스트, 버그 리포팅)도 정의되어 있습니다. 이 문서는 요청에 따라 기획자, 디자이너, 프론트엔드, 백엔드만 다뤘습니다. 정의는 [`agile-issue-rule.md`](../agile-issue/agile-issue-rule.md)의 「Role 정의」를 보세요.
